## 1. STRESZCZENIE ZARZĄDCZE

Długomat to **bardzo dojrzały, ambitny i rozległy** projekt SaaS legaltech (generowanie pism procesowych AI dla osób zadłużonych w PL). Kod jest:

- ✅ **Typeczysty** — `tsc --noEmit` przechodzi bez błędów (przy ~171 000 LOC TS/TSX).
- ✅ **Dobrze udokumentowany inline** — kluczowe moduły (AI pipeline, RBAC, webhook Stripe) mają obszerne komentarze opisujące flow, auth i fallbacki.
- ✅ **Architektonicznie poprawny** — wyraźny podział na warstwy (`app/` → `api/` → `lib/<domena>/`), RLS w Supabase, fallback chain dla AI, circuit breaker, idempotency.
- ⚠️ **Przerośnięty (over-engineered) względem etapu** — 152 tabele DB, 195 route'ów API, 88 poddomen w `lib/`, z czego **znaczna część to martwy lub półmartwy kod** (22 martwe tabele, dwie równoległe wersje frontendu, dead `llm-client.ts`).
- 🔴 **Niegotowy na produkcję w kilku krytycznych miejscach** — rate-limiting in-memory (nie działa na serverless/skalowaniu poziomym), niedomknięta idempotency w `/api/ai/generate`, 366× `as any`, niespójność env vars między `.env.example` a kodem.

**Ogólna ocena dojrzałości: 7/10** — solidny fundament, ale wymaga **konsolidacji** (usunięcie martwego kodu) i **utwardzenia produkcyjnego** (rate-limit, idempotency, monitoring) przed launchem.

## 4. AUDYT BACK-END

### 4.1 Middleware (Edge) — `apps/web/middleware.ts` (199 LOC)

**Funkcje:**

| Funkcja | Kto wywołuje | Kiedy | Zwraca | Zależności |
|---|---|---|---|---|
| `middleware(request)` | Next.js runtime (Edge) | każdy request poza static/_next | `NextResponse` (next/redirect/429) | rate-limit, supabase ssr, csp |
| `edgeCorrelationId(headers)` | `middleware` | start requestu | string (x-request-id) | crypto.randomUUID |
| `enforceRouteGuards(request, response, userPresent)` | `middleware` | po session refresh | redirect lub passthrough | — |

**Co robi (kolejność):**
1. **Edge rate-limit per IP** — `rateLimit('edge:'+clientId, RATE_LIMIT_PROFILES.edge)` (120/min). 429 jeśli przekroczone.
2. **CSP nonce + correlation_id** — generuje nonce, ustawia `x-nonce`, `x-request-id`, `x-pathname`.
3. **v5 cookie toggle** — `?v5=on|off` ustawia cookie.
4. **Supabase session refresh** — `supabase.auth.getUser()`.
5. **Route guards** — `/panel/*` anon → `/auth/sign-in?next=`; `/auth/*` zalogowany → `/panel`.
6. **`applySecurityHeaders`**.
- DEV_PREVIEW (`NEXT_PUBLIC_DEV_PREVIEW=1`) omija guardy (tylko non-prod).

🔴 **BŁĄD (#2):** Rate-limit działa **in-memory** (Map w `lib/security/rate-limit.ts`). Na Edge runtime / serverless każda instancja (i każdy region) ma własną mapę → limit **nie jest globalny**, łatwo go obejść; po redeploy/scale-out resetuje się. Sam kod to przyznaje (komentarz: "docelowo Upstash Redis"). **To blokuje skuteczny rate-limit produkcyjny.**

### 4.5 AI — pipeline generacji

**`lib/ai/apipod-client.ts` (481 LOC) — REALNY klient LLM (15 importerów):**
- Fallback chain: **APIPod** (`APIPOD_API_KEY`+`APIPOD_BASE_URL`) → **Anthropic direct** (`ANTHROPIC_API_KEY`) → `AiUnavailableError`.
- `complete(req)` — retry 2×/backend, backoff 400ms→1.6s, timeout 60s, circuit breaker (`anthropicCircuit`), `withRetry`+`classifyAnthropic`.
- `completeStreaming(req)` — prawdziwy SSE (Anthropic Messages stream), fallback do `complete()`.
- `sendApipodRequest(legacy)` — adapter dla starego API (qa-knowledge, virtual-judge, pdf/redaction).

**`lib/ai/generation-pipeline.ts` (319 LOC) — `runGenerationPipeline(input)`:**
1. Budget guardrail (`assertWithinBudget` → `BudgetExceededError` → konwersja na `AiUnavailableError`).
2. `loadActivePromptTemplate(caseType)`.
3. `validateRequiredVariables` — brakujące pola → `AiUnavailableError`.
4. RAG: `retrieveContext(query, {k:5, tags})`.
5. Compose prompt + RAG block.
6. **Generator** (Sonnet) `complete({role:'generator'})`.
7. **Validator** (Haiku) — JSON checklist, score 0-100.
8. **Escalator** (Opus) jeśli score < 70 → re-walidacja best-effort.
9. Zwraca markdown + metryki (tokeny, koszt, ragSource, promptHash PII-safe, finalRole).

**Endpoint `POST /api/ai/generate` (314 LOC) — SSE:**
- Auth (JWT) → chaos flag (`DLUGOMAT_AI_DEGRADE`) → rate-limit per-user (5/min) + per-IP → **idempotency** → load case (RLS + defense-in-depth `user_id` check) → stream (heartbeat 15s, soft-stream co akapit).
- Eventy SSE: `status`, `meta`, `delta`, `validation`, `done`, `error`.

🔴 **BŁĄD KRYTYCZNY (#3):** W `/api/ai/generate` `reserveIdempotency` jest wywoływane, ale `completeIdempotency` / `abortIdempotency` są **zaimportowane i NIGDY nie wywołane**. Skutek: po pierwszym żądaniu z `Idempotency-Key` rezerwacja zostaje w stanie `in_progress` **na zawsze** (do TTL 24h). Każde kolejne żądanie z tym samym kluczem dostaje **409 idempotency_in_progress** — nawet po pełnym, udanym wygenerowaniu. Klient z retry-logiką (np. po zerwaniu SSE) zostaje permanentnie zablokowany. **Idempotency jest funkcjonalnie zepsute.**

🟡 **UWAGA:** Endpoint reklamuje "SSE streaming", ale faktycznie używa **blokującego** `runGenerationPipeline` i dopiero potem "soft-streamuje" gotowy markdown co akapit (35ms). Prawdziwy per-token streaming (`completeStreaming`) istnieje, ale nie jest podpięty. To świadoma decyzja (komentarz w kodzie), ale UX "na żywo" jest pozorny — user czeka na cały pipeline (Sonnet+Haiku+ew. Opus) zanim zobaczy pierwszy znak.

### 4.7 Płatności — `lib/payments/` + webhook Stripe

**`app/api/stripe/webhook/route.ts` (562 LOC):** `runtime=nodejs`, `dynamic=force-dynamic`.
- POST: rate-limit → `constructWebhookEvent` (weryfikacja podpisu) → switch.
- Handlery: `handleCheckoutCompleted` (paid, case→paid, case_events, promo redemption, referral conversion, Fakturownia invoice — wszystko best-effort), `handleCheckoutExpired`, `handleChargeRefunded` (sync `refunds`), `handlePaymentFailed` (recovery email z dedupKey).
- Idempotency: per-row status check (BRAK dedykowanej tabeli na `event.id`).

🔴 **BŁĄD (#5):** Idempotency webhooka oparta wyłącznie o status wiersza, **bez tabeli dedup na `event.id` Stripe**. Stripe **gwarantuje at-least-once delivery** (te same eventy mogą przyjść wielokrotnie). Bez dedup po `event.id` ryzyko: podwójna faktura Fakturownia, podwójna konwersja referral, podwójny credit. Tabela `idempotency_records` istnieje w DB, ale webhook jej **nie używa**.

🔴 **BŁĄD (#6):** Liczne `as any` w webhooku (komentarz: "typed Database stale for recent schema columns"). Oznacza, że **wygenerowane typy `lib/db/types` są nieaktualne** względem migracji → utrata bezpieczeństwa typów w krytycznej ścieżce płatności. Globalnie **366× `as any`** w projekcie.

### 4.8 Powiadomienia — `lib/notifications/dispatch.ts` (204 LOC)

`dispatchNotification(input, {dedupKey})`:
- Używa **service role** (omija RLS — CRON/webhook adresuje do dowolnego usera).
- Idempotency: soft-skip jeśli `status='sent'` z dziś dla (template, recipient) — **bez constraintu DB**.
- Render (email/sms) → insert `notifications` (scheduled) → send (Resend/SMSAPI) → update (sent/failed).
- Push channel: rzuca "jeszcze nie obsługiwany" (placeholder).

🔴 **BŁĄD (#7):** Idempotency `dispatchNotification` to **TOCTOU race** — sprawdza SELECT, potem INSERT, bez unikalnego indeksu w DB. Dwa równoległe wywołania (np. CRON + webhook) wyślą **dwa maile**. Brak `UNIQUE(user_id, template, recipient, date)` w schemacie.

🟡 **BŁĄD (#8):** Komentarz mówi o idempotency po `(template, recipient, deadline_id)`, ale faktyczny SELECT **nie filtruje po `deadline_id`** — różne deadline'y tego samego typu w jednym dniu zostaną zdeduplikowane błędnie (pominięte powiadomienie).

### BŁĄD #1 — 🔴 P0 — Duplicate content: `/v5/*` w sitemap, brak blokady w robots
- **Plik:** `apps/web/app/sitemap.ts` (linie 75–84), `apps/web/app/robots.ts`.
- **Opis:** 10 tras `/v5/*` (duplikat marketingu) jest w sitemapie (priority 0.55–0.7) i NIE jest zablokowanych w robots.txt. Google zaindeksuje dwie wersje tych samych podstron.
- **Skutek:** Kara za duplicate content, kanibalizacja słów kluczowych, rozmycie PageRank, gorszy ranking.
- **Naprawa:** (a) Zdecydować: `/v5` to przyszły design (→ promować do `/` i usunąć stare) albo eksperyment (→ usunąć z sitemap + dodać `disallow: ["/v5/"]` w robots + `<meta robots noindex>` na layout v5 + `rel=canonical` do `/`). NIE zostawiać obu indeksowanych.

### BŁĄD #2 — 🔴 P0 — Rate limiting in-memory (nieskuteczny na produkcji)
- **Plik:** `apps/web/lib/security/rate-limit.ts` (Map `buckets`), używany w `middleware.ts` + wszystkich route'ach.
- **Opis:** Token bucket w pamięci procesu. Na Vercel/serverless każda instancja/region ma własny stan; po redeploy reset.
- **Skutek:** Atakujący rozkłada żądania na instancje → limit obejdzie. Brak ochrony przed floodem AI (kosztowne!), brute-force auth.
- **Naprawa:** Wdrożyć backend rozproszony — Upstash Redis REST (Edge-safe) lub Supabase-backed (tabele `rate_limit_window` już istnieją!). Zachować in-memory jako L1 cache + Redis L2.

### BŁĄD #3 — 🔴 P0 — Idempotency w `/api/ai/generate` nigdy nie domykana
- **Plik:** `apps/web/app/api/ai/generate/route.ts` (import linie 41–43; użycie linia 156).
- **Opis:** `reserveIdempotency` wywołane, ale `completeIdempotency`/`abortIdempotency` zaimportowane i NIGDY niewywołane. Po sukcesie/błędzie rezerwacja zostaje `in_progress`.
- **Skutek:** Każde kolejne żądanie z tym samym `Idempotency-Key` → 409 przez 24h (TTL). Retry po zerwaniu SSE = trwała blokada generacji.
- **Naprawa:** W bloku `try` po `writeEvent("done",…)` wywołać `completeIdempotency({scope:idemScope,key:idemKey,result,http_status:200})`; w `catch`/`cancel` wywołać `abortIdempotency(...)`. Uwaga: w streamingu trzeba domknąć wewnątrz `start(controller)` (nie po `return new Response`).

### BŁĄD #7 — 🔴 P0 — TOCTOU race w `dispatchNotification` (podwójne maile)
- **Plik:** `apps/web/lib/notifications/dispatch.ts` (linie 59–80, 105–121).
- **Opis:** Idempotency = SELECT potem INSERT, bez unikalnego indeksu. Współbieżne wywołania (CRON + webhook) przejdą oba checki.
- **Skutek:** Podwójne/zwielokrotnione maile i SMS-y do klienta (spam, koszty SMSAPI).
- **Naprawa:** Dodać `UNIQUE INDEX ON notifications (user_id, template, recipient, deadline_id, (created_at::date)) WHERE status IN ('sent','scheduled')` i zmienić insert na `ON CONFLICT DO NOTHING` z odczytem istniejącego wiersza.

### BŁĄD #8 — 🟠 P1 — Dedup ignoruje `deadline_id` (pominięte powiadomienia o terminach)
- **Plik:** `apps/web/lib/notifications/dispatch.ts` (SELECT linie 62–71).
- **Opis:** Komentarz deklaruje dedup po `(template, recipient, deadline_id)`, ale SELECT NIE filtruje `deadline_id`.
- **Skutek:** Dwa różne deadline'y tego samego typu w jednym dniu → drugi błędnie zdeduplikowany (klient nie dostanie alertu o ważnym terminie sądowym!). To **wysokie ryzyko prawne** dla produktu legaltech.
- **Naprawa:** Dodać `.eq("deadline_id", input.deadlineId ?? null)` do SELECT (oraz uwzględnić w UNIQUE z #7).
